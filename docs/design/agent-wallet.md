# Agent wallet

A person's own USDC wallet on Base. Their AI agents spend from it within
limits the person sets, on any site that takes x402. INITE services are
among those sites: they take x402 through the crypto rail (#207).

## Why a real wallet and not a balance in billing

A balance in billing works only on INITE services. A USDC wallet works on any
site that takes x402: the agent pays with a signed USDC authorization, and
the same signature is valid wherever the seller accepts USDC on Base.

## Who holds what

| What | Who | Note |
|---|---|---|
| The wallet | The person | A Turnkey sub-organization per person. The root user is the person's passkey. |
| Withdrawing and exporting | Only the person, with the passkey | Billing has no path to the money outside the agent's limits. |
| The agent's key | Billing, generated by billing itself | A non-root user in the person's sub-organization, constrained by the policies below. |
| Creating sub-organizations | Billing's key in our parent organization | It can create sub-organizations but cannot sign inside them. |

Turnkey isolates sub-organizations, so the parent organization cannot sign
in a person's wallet. We don't hold the person's money, which avoids the
custodian role and its legal and theft exposure. We operate only a limited
key the person can revoke.

## Agent limits

The limits are enforced in two places.

1. **Turnkey policy** on the agent's user, enforced by Turnkey itself:
   - signs only EIP-712 `TransferWithAuthorization` (`eth.eip_712.primary_type`);
   - only on the USDC contract on Base (`eth.eip_712.domain`: chainId 8453,
     verifyingContract USDC);
   - `eth.eip_712.message['value']` is at most the per-payment limit;
   - no transactions and no other signatures.

   Even with the agent's key and our server compromised, nobody gets more
   than one payment of at most the per-payment limit per signature.
2. **Billing** enforces:
   - limits per day and per month, and an optional list of allowed sites;
   - a log of every payment: site, amount, what was bought, agent;
   - an optional confirmation step above a threshold: the agent gets "needs
     confirmation", and the person confirms in the cabinet or on their phone
     with the passkey.

Defaults: $10 per payment, $20 a day, $50 a month. The person can change them
for each agent.

## Who is who: identity in Auth, money in billing

The rule: **INITE Auth answers "who is acting and on whose behalf, with what
rights". Billing answers "what money and how much is left".** Neither service
duplicates the other's job. They are linked through the agent's DID and the
grant ID.

### The agent in Auth

- **The agent is a principal with its own DID** (`did:key`, like a person's),
  not just an OAuth client:
  - it gets its DID the first time a person connects it;
  - the DID document names the controller (the person's DID), the agent's
    public keys (DPoP, HTTP Message Signatures) and the client it runs as
    (`client_id`, DCR or CIMD).
  - One program (client) connected by two people is two agents with two DIDs.
- **Agent token:**
  - `sub` = the person's DID;
  - `act` = `{ sub: <agent DID>, client_id }`;
  - `authorization_details` (RAR) of type `inite_wallet` with the limits:
    `{ per_payment, daily, monthly, asset: "USDC", network: "eip155:8453", merchants? }`;
  - `aud` = the resource (`billing.inite.ai/mcp`);
  - bound to the agent's key with DPoP, so a stolen token without the key is
    useless.

  Auth already has the `act` claim (token exchange), RAR and DPoP. What's new:
  stamping `act` with the agent's DID on the ordinary MCP sign-in
  (authorization code + DCR), and the RAR type `inite_wallet`.
- **Consent.** The Auth screen says "Agent «X» (client Y) asks to pay from
  your INITE wallet: up to $10 at a time, $20 a day". The person confirms with
  the passkey. The limits are recorded in the grant, and Auth's grant is the
  only source of truth for them.
- **Revocation and limit changes.** These happen in the INITE ID account.
  Auth sends billing an SSF event: CAEP `session-revoked` on revocation,
  `token-claims-change` on a limit change (Auth already sends both). Billing
  removes or updates the agent's user in Turnkey.

### The agent in billing

- **The wallet** belongs to the person: Turnkey sub-organization, root =
  passkey.
- **The agent's right** is a record (person DID, agent DID, Auth grant ID) →
  the agent's Turnkey user and its policy. The policy's limits are taken from
  `authorization_details`, not entered separately.
- **Every request** from the agent to billing carries Auth's token. Billing
  checks the signature, the audience, DPoP and the `act` claim; finds the
  right by (`sub`, `act.sub`); and checks the day and month limits against its
  own payment log.

### Proving the link

- **For the person:** Auth records the wallet address as a linked wallet of
  the person, the way it already links TON wallets with proof of ownership.
- **For the agent:** the agent's DID document lists the address it pays
  from. A seller can see that the payment comes from "agent X of person Y,
  verified by INITE".

### Outside INITE

- **Money.** The agent pays through billing's MCP `pay` on any x402 site. The
  seller sees an ordinary USDC payment on Base.
- **Identity, as a later stage.** Billing signs the agent's outgoing requests
  with HTTP Message Signatures (Web Bot Auth: `Signature-Agent`, a key
  directory at Auth). Sites behind Cloudflare and others can then recognise a
  verified agent and not take it for a bot. Auth can also issue the agent a
  verifiable credential, "agent of DID … with these limits" (OID4VCI). Auth
  already issues VCs.

## For the agent: MCP

Tools on billing's MCP server (`/mcp`, Auth token with `act` and
`authorization_details` of type `inite_wallet`):

- `wallet_balance`: USDC balance and the remaining day and month limits.
- `wallet_address`: the address and a QR code for topping up.
- `pay` with `{ url, method?, body?, maxAmount }`:
  - billing makes the request to the url;
  - on 402 it reads the terms and checks network, token, amount and site
    against `maxAmount` and the limits;
  - it signs through Turnkey and repeats the request with the signature;
  - it returns the seller's response and records the payment.

  This works with any x402 site, INITE services included.
- `payments`: the agent's payment history.

On our own sites' `/mcp/account` (neuralcosmology, mikefluff.com),
`create_checkout` can pay from the wallet straight away when the agent has
`wallet:pay`.

## For the person: the cabinet (billing.inite.ai/wallet)

- **Creating the wallet.** Sign in with INITE ID, create a passkey, and the
  sub-organization and address are created.
- **Topping up.**
  - Send USDC to the address on Base. We show the address and a QR code.
  - By card through an on-ramp provider (Coinbase Onramp, or the on-ramp
    built into Turnkey). We don't sell crypto ourselves; the provider does.
- **Connected agents.** Each agent's limits, history and a "Revoke" button.
  Revoking deletes the agent's user in Turnkey, which takes effect at once.
- **Withdrawing** to any address with the passkey. Billing doesn't take part.

## Connecting an agent

1. **Authorization.** The agent connects to billing's MCP. The 401 response
   points it to Auth (RFC 9728). It registers (DCR or CIMD) and requests
   `authorization_details` of type `inite_wallet`.
2. **Consent in Auth.** The person confirms the limits with the passkey. Auth
   creates the agent's DID and the grant, and issues a token with `act`.
3. **The right in the wallet.** At the agent's first request, billing sees a
   new grant. Adding a user to the person's sub-organization needs the root
   user's signature, so billing asks the person to confirm with the same
   passkey. A wallet passkey created with RP ID `inite.ai` works on both
   auth.inite.ai and billing.inite.ai, so this can be the same tap as the
   consent: the consent screen sends the request to Turnkey.
4. **Agent user.** Billing generates the agent's Turnkey key and creates a
   non-root user with the policy from the limits. The key never leaves
   billing.

## Stages

1. **Auth: the agent as a principal.**
   - the agent's DID and DID document;
   - `act` with the agent's DID in authorization code + DCR;
   - RAR type `inite_wallet`;
   - a consent screen with limits;
   - SSF events to billing (`session-revoked`, `token-claims-change`) for the
     agent's grant.
2. **Billing: wallet and cabinet.** Sub-organization with passkey (RP ID
   `inite.ai`), address, balance, top-up by transfer, withdrawal. Link the
   wallet to the person in Auth.
3. **Billing: agents.**
   - the right (person DID, agent DID, grant), the agent's Turnkey user and
     policy from RAR;
   - limits and log;
   - MCP `wallet_balance` / `wallet_address` / `pay` / `payments`;
   - revocation by SSF.
4. **Card top-up** through an on-ramp.
5. **Sites and outside world:**
   - paying from the wallet in our sites' `create_checkout`;
   - confirmation above the threshold (CIBA, already on Auth's roadmap);
   - Web Bot Auth signatures and the agent's VC.

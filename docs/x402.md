# x402: agents pay a checkout session themselves

x402 is a way to pay a crypto-rail invoice. An AI agent with a wallet pays a
checkout session in USDC on Base, from a signed authorization, with no page
and no human in the loop.

## How it fits the crypto rail

1. **The session offers x402.** `POST /v1/checkout/sessions` returns
   `x402Url` next to `checkoutUrl` whenever x402 is available, meaning both of
   these hold:
   - the crypto rail is on and takes Base;
   - the x402 block in the crypto admin is complete.

   The URL carries the session's link token, the same token the checkout
   link carries.
2. **No payment header: 402 with the terms.** `GET x402Url` opens, or
   reuses, the session's ordinary crypto invoice: Base, USDC, the rail's
   wallet, a unique amount. The answer is 402 with the terms:
   - v2: the `PAYMENT-REQUIRED` header;
   - v1: the JSON body.
3. **With a payment header: check and settle.** The agent repeats the request
   with `PAYMENT-SIGNATURE` (v2) or `X-PAYMENT` (v1), carrying an EIP-3009
   `transferWithAuthorization`. It must be signed for exactly that amount, to
   that wallet. Billing then:
   - checks the signature, the amount, the recipient and the validity window;
   - checks that the authorization is unused on chain and that the payer
     holds the amount;
   - simulates the call;
   - claims the authorization in `x402_payments`, so it can only be sent once;
   - has the relayer sign and broadcast it.

   The answer is 200 with `PAYMENT-RESPONSE` / `X-PAYMENT-RESPONSE`.
4. **The watcher settles the order.** The crypto watcher sees the transfer
   into the wallet, matches it to the invoice by amount, and the order is paid
   once the transfer is final. This is the same processor, ledger and
   confirmations as a manual crypto payment. The URL then answers 200,
   `status: "paid"`.

There is no second wallet and no separate ledger. Settled x402 payments show
up in the crypto admin like any other transfer.

## Keys

Nothing secret is in billing's environment, and nobody types or copies a
secret.

| What | Where | What a thief gets |
|---|---|---|
| The receiving wallet | Not on the server: a receive-only address in the crypto settings | Nothing to steal |
| The fee wallet (relayer) | Turnkey enclave; the private key never leaves it | — |
| Billing's Turnkey API key | Made by billing itself (`x402_relayer_keys`); only the public half is ever shown | Signatures the policy allows: only settling real payments into our wallet |

The payer's signature fixes the amount, the recipient and the deadline.
Whoever submits it cannot redirect the money. Keep only fee money on the
relayer, a few dollars of ETH on Base.

## Setup: admin → Crypto → x402

1. **In Turnkey, create the fee wallet.** Create a wallet with one Ethereum
   account, then fund that account with a little ETH on Base.
2. **In Turnkey, create the API user.** Create a **non-root** API-only user,
   for example `billing-x402`. Root users bypass policies, so it must not be
   one.
3. **In billing admin, create the key.** Press **Create key**. Billing makes a
   P-256 key pair and shows the public key. Add it to the `billing-x402` user
   in Turnkey as an API key.
4. **In billing admin, fill in the IDs.** Enter the Turnkey organization ID,
   the fee wallet address and the API user's ID, then save.
5. **In Turnkey, add the policy.** Copy the policy the page shows, already
   filled in with our addresses, and create it in Turnkey. It lets that user
   sign only USDC `transferWithAuthorization` calls:
   - on Base (chain 8453), from the fee wallet;
   - to our wallet: `data[98..138]` is the recipient argument;
   - with no ETH attached and the fee capped.

   Anything else is refused by Turnkey, and billing reports it as a failed
   settlement.

The block says **Accepting** once everything is in place, and shows the fee
wallet's balance. **Replace key** retires the old key in billing at once; then
swap the key in Turnkey.

## Limits in code

Set in `src/adapters/crypto/x402/relayer.ts` (`DEFAULT_LIMITS`):

| Limit | Value |
|---|---|
| Max fee per gas | 0.5 gwei. Above that, billing answers `network_busy` and nothing is sent. |
| Max cost of one settlement | 0.0001 ETH |
| Fees over 24 hours | 0.003 ETH. Above that, billing answers `fee_budget_exhausted`. |

## Error reasons

All of these come back with 402 and fresh terms:

| Reason | Meaning |
|---|---|
| `invalid_amount` | The authorization is not for the exact invoiced amount. |
| `invalid_recipient` | The authorization pays someone other than our wallet. |
| `invalid_network` | The authorization is not for Base. |
| `invalid_asset` | The token is not USDC. |
| `expired` / `not_yet_valid` | The validity window is closed, or closes too soon to settle. |
| `invalid_signature` | The signature does not match the authorization. |
| `insufficient_funds` | The payer does not hold enough USDC. |
| `settlement_would_fail` | The simulation was refused on chain. |
| `network_busy` | Fees are above the cap. |
| `fee_budget_exhausted` | The 24-hour fee budget is spent. |

An authorization someone else already put on chain still paid our wallet, so
it is answered 200 and the watcher settles it.
